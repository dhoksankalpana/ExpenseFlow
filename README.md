# ExpenseFlow — Expense Voucher Management System

## 1. Project Overview

ExpenseFlow is a full-stack expense voucher management application designed to manage expense claims through employee submission, director approval or rejection, and accounts review.

### User roles

- **Employee:** Create vouchers, edit or delete their own drafts, and submit vouchers with a signature.
- **Director:** Review submitted vouchers, approve them with a signature, or reject them with a reason.
- **Accounts:** View vouchers across the organization.

### Technology stack

**Frontend**
- React
- Vite
- React Router
- Axios
- CSS
- Lucide React icons
- Recharts

**Backend**
- Node.js
- Express
- PostgreSQL
- `pg` database driver
- JWT authentication
- HTTP-only cookies
- bcryptjs password hashing
- Zod validation
- Helmet, CORS, and CSRF protection
- Multer for signature uploads

## 4. Database Setup

Create a PostgreSQL database for ExpenseFlow. For example, using `psql`:

```sql
CREATE DATABASE expenseflow;
```

Connect to the database and apply the migration from the project root:

```powershell
psql -U YOUR_DB_USER -d expenseflow -f .\backend\migrations\001_initial_schema.sql
```

Replace `YOUR_DB_USER` with your PostgreSQL username. Enter your PostgreSQL password when prompted.

The migration creates the following tables:

| Table | Purpose |
|---|---|
| `departments` | Organization departments |
| `users` | User accounts, roles, and department assignments |
| `vouchers` | Expense voucher details and current status |
| `voucher_approvals` | Submission, approval, and rejection history |
| `audit_logs` | Records of important application actions |

The migration also creates a voucher-number sequence and indexes used for common queries.

New vouchers receive a unique number generated by PostgreSQL in the format `EXP-YYYY-000001` (the sequence number continues increasing).

## 9. API Documentation

All API endpoints use the `/api` prefix.

### Health and authentication

| Method | Endpoint | Purpose |
|---|---|---|
| GET | `/api/health` | Check API availability |
| GET | `/api/auth/csrf` | Obtain a CSRF token |
| GET | `/api/auth/departments` | List departments for registration |
| POST | `/api/auth/register` | Register an employee account |
| POST | `/api/auth/login` | Authenticate a user |
| POST | `/api/auth/logout` | Clear the login cookie |
| GET | `/api/auth/me` | Retrieve the current authenticated user |

### Vouchers

| Method | Endpoint | Purpose |
|---|---|---|
| GET | `/api/vouchers` | List vouchers permitted for the current role |
| POST | `/api/vouchers` | Create an employee draft |
| GET | `/api/vouchers/:id` | Retrieve voucher details and history |
| PUT | `/api/vouchers/:id` | Edit an employee's own draft |
| DELETE | `/api/vouchers/:id` | Delete an employee's own draft |
| POST | `/api/vouchers/:id/submit` | Submit a draft with an employee signature |
| POST | `/api/vouchers/:id/approve` | Approve a submitted voucher with a director signature |
| POST | `/api/vouchers/:id/reject` | Reject a submitted voucher with a required reason |
| GET | `/api/vouchers/:id/signatures/:kind` | Retrieve an authorized voucher signature |

The `:id` parameter identifies a voucher. The signature `:kind` is `employee` or `director`.

### Important request details

- Login accepts an email address and password.
- Registration accepts `fullName`, `email`, `password`, and `departmentId`. New registrations receive the employee role.
- Creating and updating a voucher uses `expenseDate`, `departmentId`, `title`, `category`, `description`, and `amount`.
- Voucher submission and approval use multipart form data with a `signature` file.
- Approval can include optional `notes`.
- Rejection requires a non-empty `rejectionReason`; `notes` are optional.
- State-changing requests must satisfy the application's CSRF protection.
- Authentication uses an HTTP-only cookie. Use a client configured to send credentials.

## 10. Voucher Workflow

1. An employee signs in and creates a draft voucher.
2. The employee can edit or delete the draft while it remains a draft.
3. The employee uploads a signature and submits the voucher.
4. A director reviews the submitted voucher and either approves it with a signature or rejects it with a reason.
5. Accounts can review vouchers across the organization.
6. Submission and decision history is recorded in `voucher_approvals`; important actions are recorded in `audit_logs`.

Employees are restricted to their own vouchers. Director and Accounts users can view vouchers across the organization. The backend enforces role and ownership restrictions for voucher operations.

## 11. Validation and Security

The application includes:

- Password hashing with bcryptjs
- JWT authentication in an HTTP-only cookie
- Role-based access control
- Server-side request validation with Zod
- CSRF protection for state-changing requests
- Security headers through Helmet
- CORS configured for the frontend origin
- Protected signature retrieval
- Database transactions for important voucher state changes
- Audit logging

Keep real credentials, environment files, and uploaded signatures private.

## 12. Assumptions and Limitations

- PostgreSQL is the application's database.
- New registrations create employee accounts; director and Accounts roles must be provisioned through an authorized process.
- A voucher starts in the draft state.
- Employee signatures are required for submission, and director signatures are required for approval.
- A rejection reason is mandatory when rejecting a voucher.
- Submitted and approved vouchers cannot be edited through the employee draft-editing operation.
- Signature images are stored as files; the database stores their references.
- Local development URLs and example environment values must be adjusted for deployment.
- This README documents the implementation and intended workflow; actual deployment, production hardening, and end-to-end tests must be verified separately.
